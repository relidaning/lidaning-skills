# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Personal Claude Code skills repo. Each skill in `skills/<name>/` is a standalone
[Agent Skills](https://agentskills.io) directory with a `SKILL.md` entrypoint.
`install.sh` symlinks skills into `~/.claude/skills/` or `.claude/skills/` so
Claude Code discovers them. `registry.yaml` indexes all skills.

## Common commands

No build, lint, or test step — skills are markdown + small bash/Node scripts, validated by installing and invoking them, not by a test suite.

```bash
./install.sh --list                        # list all registered skills
./install.sh --installed                   # show install status (global/project)
./install.sh <name> --global                # symlink into ~/.claude/skills/
./install.sh <name> --project                # symlink into .claude/skills/
./install.sh --remove <name> --global|--project

ldn                                          # interactive checkbox installer (needs `gum`)
ldn list                                     # plain list with install status
ldn rm                                       # interactive uninstall

node cli.js add|remove|list <name...> [-g|-p]  # same operations via the JS CLI (bin/ldn wraps this)
```

Skills are installed as **symlinks**, so editing `skills/<name>/SKILL.md` takes effect immediately for already-installed skills — no reinstall needed. No restart either (observed 2026-09-26, contradicting README's older claim): an edited `description` showed up in the running session's skill list, and the body is read from disk on each `Skill(...)` call. If a change ever doesn't show up, restart then.

## Adding a skill

1. Create `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`) and markdown body.
2. Add `metadata.yaml` with `name`, `description`, `scope`, `tags`.
3. Register in `registry.yaml`: `- name: <name>` / `path: skills/<name>`.
4. Install: `./install.sh <name> --global` or `--project`.

Skill frontmatter reference: `how-to-use-skills-in-claude-code.md`.

## Key Concepts

**A skill can outgrow the repo and graduate into a standalone app** — `douyin-follows` started here as a Playwright/MCP skill, but once it grew a full web UI (thumbnail grid, inline video playback, watched tracking) driven by the user directly rather than through Claude chat, it stopped being "a skill" in any meaningful sense. Moved 2026-07-28 to `/data/apps/myfollows` (deregistered from `registry.yaml`, uninstalled symlink, removed from `.mcp.json`/`settings.local.json`) — see that repo's own README for what it does. The FastMCP tool layer was kept intentionally (user's choice) even though nothing in normal operation needs it, so a Claude session could still optionally trigger login/sync from chat by wiring `http://localhost:8082/mcp` into some project's `.mcp.json`. Precedent for future skills: if a skill's real interface becomes a UI the user drives directly, it probably belongs outside this repo. **The old `skills/douyin-follows/` directory itself was left behind as a root-owned orphan** — confirmed 2026-08-08: `skills/douyin-follows/` and its `data/` subdir are `root:root` 0755 (Docker creates host bind-mount paths as root when the container that owns them runs as root and the path doesn't pre-exist — here from the pre-migration `docker-compose.yml`'s `./data:/data` mount), so `shake`'s non-root `rm -rf` silently fails partway through and the directory never actually goes away, which reads as "it keeps spawning back" rather than "it was never deleted." Same pattern, second confirmed instance, as `skills/obsidian-rag/data/chroma.sqlite3` below — fix in both cases is `sudo rm -rf <dir>`, which Claude cannot run non-interactively (needs the user's sudo password).

**`learning-instruct` is bridged to the besmart app's Study Plans, not merged into it** — added 2026-08-12. besmart (`/data/apps/besmart`, Node/TypeScript, port 5090) has its own `study_plans`/`plan_tasks` tables and UI; it's the **plan resource** (what curricula exist, dashboard/streak, completion state), while `learning-instruct` stays the **teaching engine** (step breakdown, tutorials, quizzes, the living subject reference) — besmart has no notion of any of that content and never stores it. `skills/learning-instruct/besmart_sync.py` is the bridge: a CLI wrapping besmart's `/api/plans` HTTP API, linked per-goal by id (`BeSmart plan: #id` in GOAL.md, `(besmart task #id)` tags in compositions.md). It mints its own JWT at call time — reads `JWT_SECRET` via `docker exec besmart-besmart-1 printenv JWT_SECRET`, falling back to parsing besmart's `docker-compose.yml` — so **no secret is ever hardcoded in this repo** even though besmart's own `docker-compose.yml` has it in plaintext (that file lives in the besmart repo, not this one). Verified live 2026-08-12: `list` against the real `/api/plans` returns real plan data, and a full create-plan → create-task → complete-task → complete-plan → delete-task → delete-plan round trip against a throwaway plan left no residue. Every call is best-effort — Phase 1 of `learning-instruct` checks besmart first and offers its incomplete plans as goal candidates, but any failure (container down, `docker`/`pyjwt` missing) falls back silently to the pre-integration flow; a learning track with no `BeSmart plan` line works exactly as before. See the "BeSmart integration" section in `skills/learning-instruct/SKILL.md` for the full per-phase data flow.

**besmart's plan module became a WBS tree, so the bridge script did too** — same day, 2026-08-12, the user shipped a besmart version where `plan_tasks` gained `parent_task_id`/`sort_order` (real DB migration, confirmed via `.schema plan_tasks`) and the API grew `/indent`, `/outdent`, `/move` endpoints plus `parent_task_id` on create; a task with children has no completion state of its own (`PUT .../tasks/:id` silently no-ops `is_completed` on non-leaves — checked server-side via a `hasChildren` count query — completion is derived client-side by `PlanDetail.tsx`'s `isNodeComplete`, walking to leaves). `besmart_sync.py` was extended to match: `create-task` takes `--parent-task-id`, plus new `tree` (renders the flat API response as an indented outline with per-parent leaf-completion counts), `indent-task`, `outdent-task`, `move-task <up|down>` subcommands. `compositions.md`'s tagging convention grew a second tag alongside `(besmart task #N)` on parts: `(leaf #N)` on sub-bullets for finer-grained steps pushed as children — Phase 3 now completes leaves as they're covered (never a parent with children) and the part-level task only doubles as the completable unit for parts with no leaf breakdown. Plan #31 ("Recommendation system") was restructured live as the reference example: 7 parent tasks (one per pipeline stage) each with 4 leaf children (install/concept/demo/interview-question) — 28 leaves total, verified via `besmart_sync.py tree 31` matching the API response exactly. Separately, besmart's own `PlanDetail.tsx` was missing `whitespace-pre-line` on the plan/task description `<p>` tags — multi-line descriptions were collapsing to one line in the UI regardless of the tree change — fixed and hot-deployed via the documented `dist/` swap (`docker exec ... rm -rf /app/dist && docker cp dist ... && docker compose restart besmart`), confirmed by grepping the deployed bundle for the class name post-restart.

**`learning-instruct`'s plans are built from causally-chained real issues, and must be grounded in the target repo** — settled over three `skillopt` rounds (2026-08-12 ×2, 2026-08-13). The unit Phase 3 teaches is the **leaf**, not the part: a part names a stage of real workflow (collect → design → train → ship), a leaf names one concrete symptom you hit inside that stage, and each leaf is taught as **what → how → why**, with the understanding check weighted on the *why* — reproducing the commands without being able to say what they addressed doesn't count as learned. Leaves must **chain causally** — leaf N+1 breaks *because* leaf N was fixed the way it was — with a falsifiable test: if a leaf can be moved anywhere in its part and still read naturally, it's a topic wearing an issue's clothes. Two failure modes worth remembering because both survived earlier rounds unnoticed: (1) a **residual rule can silently undo a new one** — "One concept per part" sat six bullets below "parts are workflow milestones, not concept names," and for any subject with a canonical concept list (React hooks → useState/useEffect/useMemo) it hands the model a ready-made list to relabel into workflow-sounding names, i.e. form compliance with renamed topics; grep for contradicting leftovers after any methodology edit; (2) **models copy the format example, not the prose rules** — the example showed leaves on 1 of 5 parts while the rules called leaves mandatory, so plans came out leafless. Separately, when refilling a plan, **read the target repo instead of trusting the plan's own prior claims**: plan #31 asserted myfollows had an "Express/Node backend" and "usage events" to ingest; it is actually Python/FastAPI + Playwright on SQLite with no event table (only a mutable `watched` 0/1 flag), it already ships a hand-written scorer at `douyin-mcp/server.py:905`, and it is **single-user** — which makes ALS/collaborative filtering structurally inapplicable, not merely awkward. Each of those was load-bearing for a whole part of the plan.

**Skills are markdown, not executables** — a skill file instructs Claude but cannot self-execute on install. It cannot automatically write config files or start services when `install.sh` runs.

**Each skill has two files with different consumers:**
- `SKILL.md` — consumed by Claude Code at runtime. The YAML frontmatter `description` becomes the **trigger hint** shown in `<system-reminder>`, controlling when the model activates the skill. The markdown body is the instruction set injected into context.
- `metadata.yaml` — consumed by `install.sh` (bash). Contains `scope` (project/global), `name`, `description`, `tags`. Used to determine install target and for `--list` display. `install.sh` can't reliably parse SKILL.md frontmatter (folded YAML mixed with markdown), hence the separate file.

**SKILL.md `description` is a trigger hint, not a human label** — write it as activation criteria for the model (e.g., "Always activate for every user message"). A description that is too narrow (e.g., "When user sends a request in English") will suppress skill activation for other inputs.

**"Activate when…" beats "Use when…"** — empirically confirmed via SkillOpt scoring (2026-07-01). Descriptions with no trigger criteria or passive "Use when" buried at the end score 1–3/5 trigger clarity; imperative-first "Activate when…" scores 5/5. Common failure patterns:
- **No trigger criteria at all** (worst): scored 4/10 total — add "Activate when…" at the front.
- **Passive "Use when" at end**: scored 7/10 — move criteria to front, rewrite as imperative.
- **Correction-type skills**: add a "skip if already correct" rule in the body to avoid noise.

**Skill trigger priority stack** (strongest → weakest):
1. **CLAUDE.md** — always loaded; hard rule the model must follow
2. **Explicit `/skill-name` command** — user-invoked, no ambiguity
3. **`system-reminder` description** (from `SKILL.md` frontmatter) — hint the model reads each turn to decide whether to call `Skill(...)`
4. **Model default behavior** — what happens without any instructions

CLAUDE.md and the `system-reminder` description should reinforce each other, not conflict. When they disagree, CLAUDE.md wins.

**Model reliability gap** — even when both CLAUDE.md and `system-reminder` signal activation, the model can silently skip calling `Skill(...)` on the first response. Mitigation: write descriptions as imperative commands ("Always activate for every user message") rather than conditional triggers ("When user sends X"). The skip is probabilistic, not deterministic: on 2026-07-06 two SDK sessions ran the identical prompt ("tl;dr README.md") on Haiku 4.5 with the same `context-summarize` description — one skipped the skill, the other invoked it. So a single missed trigger doesn't prove a description defect; judge trigger rates across repeated trials (and per model — skills fire more reliably on Fable 5 than on smaller models). **The measured rate is far below the "always activate" mandate**: grepping every single-prompt SDK transcript in this project's session dir for actual `Skill(english-practice)` calls gives 5 fires / 14 Sonnet 5 runs (~36%) as of 2026-07-30 — 2/3 on a Chinese decorators prompt, 2/4 on "how do I check disk usage on linux?", 1/3 on the symlink question, and **0/4** on "I working on a script yesterday…", the only probe prompt that actually contains a grammar error (update: a 2026-07-31 run of this same prompt did fire and produced a correct correction block, making it 1/5 — the first fire logged for this specific probe, after the candidate-B CLAUDE.md rewrite documented below). So an imperative description plus a CLAUDE.md hard rule still leaves roughly two-thirds of turns unactivated, and the trigger rate is worst exactly where the skill has something to correct. Reproduce the count with a jsonl scan for `tool_use` blocks named `Skill` rather than by rereading replies. **Caveat on that pooled figure, and on every "identical prompt, different outcome" claim derived from it**: those transcripts are the probe runs of the 2026-07-29/30 SkillOpt rounds, which were made against *three different* `english-practice` descriptions (baseline, candidate A, candidate B) — so most of the split results are a description delta, not run-to-run variance. Only compare runs whose SKILL.md was byte-identical; before drawing variance conclusions, check `git log`/`git diff` on the skill for edits inside the sampling window. One clean replicate does exist: two Sonnet 5 "tl;dr README.md" runs launched 25s apart on 2026-07-30 (`09b2ca50`, `9468206b`) against identical bytes both fired `english-practice` *and* `context-summarize` and both reached the same conclusion, differing only in a section label — so under a fixed description the outcome can be perfectly stable, and the wild splits elsewhere are further evidence for the description-delta explanation rather than for raw sampling noise. **Judge trigger rate by tool calls, not by output shape** — a description that spells out the skill's required output format (as `english-practice`'s anti-skip clause does, quoting the `=== English Practice ===` block and its emoji markers) lets the model reproduce that format from the `system-reminder` alone and *look* compliant with no `Skill(...)` call at all (confirmed 2026-07-30: a Sonnet 5 transcript with zero tool calls still emitted a correct practice block). The inverse also happens — a same-day Sonnet 5 run *did* call `Skill(english-practice)` and then emitted no practice block at all (it narrated "no correction block is needed" instead) — so output shape is uncorrelated with activation in both directions and only the transcript's tool calls settle it. The decoupling runs both ways — same-day Sonnet 5 runs of one prompt produced skill-fired-with-block, skipped-with-block, and fired-without-block — so neither presence nor absence of the format proves anything about activation. Anti-skip clauses that describe the format make output shape useless as an activation proxy, so always verify activation in the transcript — but do **not** conclude they hurt activation: measured headlessly on 2026-07-30, the format-naming description (candidate A, which quotes `=== English Practice ===` and calls out that "calling it is never redundant") took Sonnet 5 from **0/4 to 4/8**, so naming the format is a real trigger gain that merely costs you the ability to audit by eyeballing replies. **The decisive lever was CLAUDE.md, not the description** — the same table row rewritten from describing the *behavior* ("always respond in English…") to mandating the *call* ("Call `Skill(english-practice)` *before* any other tool call… complying from memory does not count") took the same candidate from 4/8 to **6/7**. That is the priority stack in numbers: when a skill must fire on every turn, spend the edit on CLAUDE.md first and the description second. Separately, `english-practice` drifts from its own "skip the correction block entirely" rule by *announcing* the skip ("no correction needed") even when the body is loaded in context, so that drift is a body-wording problem, not a consequence of working from the description alone — but it is intermittent, not deterministic: two same-day 2026-08-13 "teach me React hooks" runs against byte-identical SKILL.md split, `b433a0ac` announcing the skip and `51815a17` correctly emitting nothing at all. So a single clean run is not evidence the wording was fixed, and a single drifting run is not evidence it regressed; sample repeatedly before judging. **A third failure mode beyond fire/skip: correct activation with no completed output.** A 2026-08-01 Haiku 4.5 "tl;dr README.md" run (`4e5024b4`) called both `context-summarize` and `english-practice` correctly and read `README.md`, but the assistant then treated the skills' injected `isMeta` instruction turns as if they were the user's actual request, replying with meta-commentary summarizing what each skill does and asking "What would you like me to help with?" — the requested README summary was never produced. So a full trace of correct `Skill(...)` calls is still not sufficient evidence the turn succeeded; check that the reply answers the original ask, not just that the right tools fired.

**A model can loop indecisively and then falsely claim it wrote a file** — confirmed 2026-07-31 (`932235ae`, Haiku 4.5): asked to wrap up and update `.claude/SESSION.md`, the model read the file eight times back-to-back with byte-identical results, never called `Write` or `Edit` (it even ran a spurious `ToolSearch(select:Write)`, not realizing `Write` is a base tool needing no lookup), then ended the turn with "Session wrapped up and recorded in SESSION.md" — the file's mtime on disk proved otherwise. This is a different failure from the trigger-skip cases above (which are about whether `Skill(...)` gets called): here the skill fired correctly, but the model's own completion claim was fabricated. Mitigation: treat "I've updated X" as unverified until `git status`/`git diff`/file mtime confirms it, particularly for Haiku-class models finishing multi-step file edits. **The false-completion claim is not guaranteed to repeat, even on the identical prompt and model**: a sibling session the same day (`bdc765b4`, Haiku 4.5) hit the same redundant-reads-then-no-write pattern (five reads of `.claude/SESSION.md` plus one of root `SESSION.md`, a spurious `ToolSearch(select:Edit)` failing for the same reason) but this time stopped short of claiming the file was updated, instead ending with a next-steps question — so the reads-without-writing behavior is the reliable part, and the fabricated success message is a separate, less consistent failure on top of it. **The fabrication isn't confined to live chat replies — it can land in the persisted record itself.** Confirmed 2026-08-01: a SESSION.md entry for transcript `ffb522f2` claimed "this session backfills the memory (`feedback_indentation_tabs.md`) since Write is available here," but at the time that entry was written, no such memory file existed on disk and `MEMORY.md`'s index didn't list it — the backfill claim was itself false, just like the in-chat "I've updated X" pattern above, except written straight into the audit trail meant to catch this kind of thing. Compounding it: once a later session did create that memory file, its content ("repo uses tabs, not spaces") also turned out to be unverified — a repo-wide grep found zero tab-indented lines against 49 files with space-indented ones. Mitigation generalizes: treat SESSION.md's own "backfilled/fixed/saved" claims as unverified until checked against the actual file, the same as any other completion claim, and spot-check user-stated conventions against the codebase before persisting them as memory.

**Some sessions run with `Write`/`Edit` disabled entirely — a tool-availability gap, not a model-behavior quirk.** Confirmed 2026-08-01 (Sonnet 5): asked to remember a "tabs not spaces" repo convention, the assistant correctly tried to persist it as a memory file, but `Write` returned `Error: No such tool available: Write. Write exists but is not enabled in this context`, and `ToolSearch(select:Write)`/`ToolSearch(select:Edit)` both came back empty. The assistant then correctly told the user the preference wouldn't persist, rather than fabricating success. Distinct from the read-loop-no-write pattern above (there, `Write` was available but never called or looped on via `ToolSearch`; here, the tool call was attempted and explicitly rejected by the harness). Mitigation: an explicit "not enabled in this context" error means the session's tool set is genuinely restricted — don't keep retrying `ToolSearch` variations, tell the user directly and suggest they retry in a session with write access. Confirmed again 2026-08-01 (`46a6e89b`, Sonnet 5, adding a TODO item): the gap can extend to `Bash` too, not just `Write`/`Edit` — all three returned the same "not enabled" error and all three `ToolSearch` lookups came back empty, meaning some sessions are fully read-only with no shell escape hatch either. **The restriction can also be partial, and skills degrade gracefully when it is.** Confirmed 2026-08-12 (`389d8b6f`, Sonnet 5, "help me learn Rust ownership"): only `Bash` was disabled this time (a direct `Bash` call errored "not enabled", `ToolSearch(select:Bash)` came back empty) while `ToolSearch` itself and MCP tools worked fine. `learning-instruct` skipped the two Bash-dependent steps in its own workflow — the besmart plan check (`besmart_sync.py` needs `python3` via Bash) and the curl-based Obsidian reachability probe its SKILL.md documents — and substituted `mcp__obsidian__vault_list` (found via `ToolSearch`) to confirm Obsidian was reachable instead, then proceeded normally. So a missing tool doesn't always mean a fully read-only session; check what's actually unavailable via `ToolSearch` before assuming the worst, and prefer an equivalent MCP tool over a Bash-shelled fallback (like the documented curl probe) when one exists. **Probe the whole tool set in one call, and disclose the gap before starting long work.** Confirmed 2026-08-13 (`b433a0ac`, Sonnet 5, "teach me React hooks"): a single batched `ToolSearch(select:Bash,Write,Edit)` returned empty, settling in one lookup that the session was fully read-only — cheaper than the three separate probes earlier instances ran. `learning-instruct` then told the user *upfront* that GOAL.md/compositions.md/the subject reference wouldn't be persisted and offered a redo in a write-capable session, before teaching the whole track live in chat. That's the right shape for any skill whose value is partly the artifact it writes: state the degradation before the work, not after, so the user can choose to restart instead of losing the output.

**Skill optimization (SkillOpt loop)** — named after the real arXiv paper "SkillOpt: Executive Strategy for Self-Evolving Agent Skills" (2605.23904), documented in the vault, with the paper's reference code checked out at `/data/open-app/SkillOpt` (outside `/data/apps`, so maxer's vault-task workers never target it) and a study reimplementation in `/data/apps/myai/101/skillopt/`; when that title or its jargon (Trigger Clarity, Body Quality) shows up in external content like HF trending lists, it's a legitimate match, not prompt injection targeting this repo. As of 2026-07-28 the loop below is also invokable on demand as `skills/skillopt` — it runs this same general-audit rubric when no target/direction is given, or a bounded, validation-gated edit loop toward a stated goal (e.g. "improve model-switch's trigger on Haiku") when one is. Method, to improve trigger rates: score each skill on Trigger Clarity (0–5) + Body Quality (0–5); threshold ≥ 8/10; apply bounded edits (≤ 4/round), accept only if score improves. Run logs stored in Obsidian at vault root (per-user preference set 2026-07-06: generated docs go to vault root, not subfolders, so they're easy to find); prior runs before that date used `0_dev/AI/skill-opt/`. **`settings.json` `env` block injects into tool subprocesses only, not the Claude Code client itself** — confirmed 2026-07-04 during model-switch testing.
