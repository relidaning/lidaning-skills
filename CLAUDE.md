# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Personal Claude Code skills repo. Each skill in `skills/<name>/` is a standalone
[Agent Skills](https://agentskills.io) directory with a `SKILL.md` entrypoint.
`install.sh` symlinks skills into `~/.claude/skills/` or `.claude/skills/` so
Claude Code discovers them. `registry.yaml` indexes all skills.

## Common commands

No build, lint, or test step — skills are markdown + small bash/Node scripts, validated by installing and invoking them, not by a test suite.

```bash
./install.sh --list                        # list all registered skills
./install.sh --installed                   # show install status (global/project)
./install.sh <name> --global                # symlink into ~/.claude/skills/
./install.sh <name> --project                # symlink into .claude/skills/
./install.sh --remove <name> --global|--project

ldn                                          # interactive checkbox installer (needs `gum`)
ldn list                                     # plain list with install status
ldn rm                                       # interactive uninstall

node cli.js add|remove|list <name...> [-g|-p]  # same operations via the JS CLI (bin/ldn wraps this)
```

Skills are installed as **symlinks**, so editing `skills/<name>/SKILL.md` takes effect immediately for already-installed skills — no reinstall needed (a fresh session restart is still required to pick up changes, per README).

## Adding a skill

1. Create `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`) and markdown body.
2. Add `metadata.yaml` with `name`, `description`, `scope`, `tags`.
3. Register in `registry.yaml`: `- name: <name>` / `path: skills/<name>`.
4. Install: `./install.sh <name> --global` or `--project`.

Skill frontmatter reference: `how-to-use-skills-in-claude-code.md`.

## Session tracking

The `coding-orchestrate` skill manages four files. Three live under `.claude/` to keep the project root clean; `README.md` stays at the root by convention:

- **`.claude/SESSION.md`** — per-session logs with goals, what was done, current state, decisions
- **`.claude/TODO.md`** — discovered tasks, format `- [ ] item`
- **`.claude/MEMORIES.md`** — things the user explicitly asked to remember
- **`README.md`** — kept current with project concepts and features

These are skill-managed, not hand-edited. When in doubt, invoke `/coding-orchestrate`.

Note: `.claude/` is gitignored, so these three files are local-only and not versioned — they can silently disappear (e.g. `TODO.md` was lost when moved under `.claude/` in commit 65d311e4 and later had to be rebuilt from `git show 65d311e4^:TODO.md`). If one goes missing, check git history from before the move.

## Key Concepts

**A skill can outgrow the repo and graduate into a standalone app** — `douyin-follows` started here as a Playwright/MCP skill, but once it grew a full web UI (thumbnail grid, inline video playback, watched tracking) driven by the user directly rather than through Claude chat, it stopped being "a skill" in any meaningful sense. Moved 2026-07-28 to `/data/apps/myfollows` (deregistered from `registry.yaml`, uninstalled symlink, removed from `.mcp.json`/`settings.local.json`) — see that repo's own README for what it does. The FastMCP tool layer was kept intentionally (user's choice) even though nothing in normal operation needs it, so a Claude session could still optionally trigger login/sync from chat by wiring `http://localhost:8082/mcp` into some project's `.mcp.json`. Precedent for future skills: if a skill's real interface becomes a UI the user drives directly, it probably belongs outside this repo. **The old `skills/douyin-follows/` directory itself was left behind as a root-owned orphan** — confirmed 2026-08-08: `skills/douyin-follows/` and its `data/` subdir are `root:root` 0755 (Docker creates host bind-mount paths as root when the container that owns them runs as root and the path doesn't pre-exist — here from the pre-migration `docker-compose.yml`'s `./data:/data` mount), so `shake`'s non-root `rm -rf` silently fails partway through and the directory never actually goes away, which reads as "it keeps spawning back" rather than "it was never deleted." Same pattern, second confirmed instance, as `skills/obsidian-rag/data/chroma.sqlite3` below — fix in both cases is `sudo rm -rf <dir>`, which Claude cannot run non-interactively (needs the user's sudo password).

**Skills are markdown, not executables** — a skill file instructs Claude but cannot self-execute on install. It cannot automatically write config files or start services when `install.sh` runs.

**Each skill has two files with different consumers:**
- `SKILL.md` — consumed by Claude Code at runtime. The YAML frontmatter `description` becomes the **trigger hint** shown in `<system-reminder>`, controlling when the model activates the skill. The markdown body is the instruction set injected into context.
- `metadata.yaml` — consumed by `install.sh` (bash). Contains `scope` (project/global), `name`, `description`, `tags`. Used to determine install target and for `--list` display. `install.sh` can't reliably parse SKILL.md frontmatter (folded YAML mixed with markdown), hence the separate file.

**SKILL.md `description` is a trigger hint, not a human label** — write it as activation criteria for the model (e.g., "Always activate for every user message"). A description that is too narrow (e.g., "When user sends a request in English") will suppress skill activation for other inputs.

**"Activate when…" beats "Use when…"** — empirically confirmed via SkillOpt scoring (2026-07-01). Descriptions with no trigger criteria or passive "Use when" buried at the end score 1–3/5 trigger clarity; imperative-first "Activate when…" scores 5/5. Common failure patterns:
- **No trigger criteria at all** (worst): scored 4/10 total — add "Activate when…" at the front.
- **Passive "Use when" at end**: scored 7/10 — move criteria to front, rewrite as imperative.
- **Correction-type skills**: add a "skip if already correct" rule in the body to avoid noise.

**Skill trigger priority stack** (strongest → weakest):
1. **CLAUDE.md** — always loaded; hard rule the model must follow
2. **Explicit `/skill-name` command** — user-invoked, no ambiguity
3. **`system-reminder` description** (from `SKILL.md` frontmatter) — hint the model reads each turn to decide whether to call `Skill(...)`
4. **Model default behavior** — what happens without any instructions

CLAUDE.md and the `system-reminder` description should reinforce each other, not conflict. When they disagree, CLAUDE.md wins.

**Model reliability gap** — even when both CLAUDE.md and `system-reminder` signal activation, the model can silently skip calling `Skill(...)` on the first response. Mitigation: write descriptions as imperative commands ("Always activate for every user message") rather than conditional triggers ("When user sends X"). The skip is probabilistic, not deterministic: on 2026-07-06 two SDK sessions ran the identical prompt ("tl;dr README.md") on Haiku 4.5 with the same `context-summarize` description — one skipped the skill, the other invoked it. So a single missed trigger doesn't prove a description defect; judge trigger rates across repeated trials (and per model — skills fire more reliably on Fable 5 than on smaller models). **The measured rate is far below the "always activate" mandate**: grepping every single-prompt SDK transcript in this project's session dir for actual `Skill(english-practice)` calls gives 5 fires / 14 Sonnet 5 runs (~36%) as of 2026-07-30 — 2/3 on a Chinese decorators prompt, 2/4 on "how do I check disk usage on linux?", 1/3 on the symlink question, and **0/4** on "I working on a script yesterday…", the only probe prompt that actually contains a grammar error (update: a 2026-07-31 run of this same prompt did fire and produced a correct correction block, making it 1/5 — the first fire logged for this specific probe, after the candidate-B CLAUDE.md rewrite documented below). So an imperative description plus a CLAUDE.md hard rule still leaves roughly two-thirds of turns unactivated, and the trigger rate is worst exactly where the skill has something to correct. Reproduce the count with a jsonl scan for `tool_use` blocks named `Skill` rather than by rereading replies. **Caveat on that pooled figure, and on every "identical prompt, different outcome" claim derived from it**: those transcripts are the probe runs of the 2026-07-29/30 SkillOpt rounds, which were made against *three different* `english-practice` descriptions (baseline, candidate A, candidate B) — so most of the split results are a description delta, not run-to-run variance. Only compare runs whose SKILL.md was byte-identical; before drawing variance conclusions, check `git log`/`git diff` on the skill for edits inside the sampling window. One clean replicate does exist: two Sonnet 5 "tl;dr README.md" runs launched 25s apart on 2026-07-30 (`09b2ca50`, `9468206b`) against identical bytes both fired `english-practice` *and* `context-summarize` and both reached the same conclusion, differing only in a section label — so under a fixed description the outcome can be perfectly stable, and the wild splits elsewhere are further evidence for the description-delta explanation rather than for raw sampling noise. **Judge trigger rate by tool calls, not by output shape** — a description that spells out the skill's required output format (as `english-practice`'s anti-skip clause does, quoting the `=== English Practice ===` block and its emoji markers) lets the model reproduce that format from the `system-reminder` alone and *look* compliant with no `Skill(...)` call at all (confirmed 2026-07-30: a Sonnet 5 transcript with zero tool calls still emitted a correct practice block). The inverse also happens — a same-day Sonnet 5 run *did* call `Skill(english-practice)` and then emitted no practice block at all (it narrated "no correction block is needed" instead) — so output shape is uncorrelated with activation in both directions and only the transcript's tool calls settle it. The decoupling runs both ways — same-day Sonnet 5 runs of one prompt produced skill-fired-with-block, skipped-with-block, and fired-without-block — so neither presence nor absence of the format proves anything about activation. Anti-skip clauses that describe the format make output shape useless as an activation proxy, so always verify activation in the transcript — but do **not** conclude they hurt activation: measured headlessly on 2026-07-30, the format-naming description (candidate A, which quotes `=== English Practice ===` and calls out that "calling it is never redundant") took Sonnet 5 from **0/4 to 4/8**, so naming the format is a real trigger gain that merely costs you the ability to audit by eyeballing replies. **The decisive lever was CLAUDE.md, not the description** — the same table row rewritten from describing the *behavior* ("always respond in English…") to mandating the *call* ("Call `Skill(english-practice)` *before* any other tool call… complying from memory does not count") took the same candidate from 4/8 to **6/7**. That is the priority stack in numbers: when a skill must fire on every turn, spend the edit on CLAUDE.md first and the description second. Separately, `english-practice` drifts from its own "skip the correction block entirely" rule by *announcing* the skip ("no correction needed") even when the body is loaded in context, so that drift is a body-wording problem, not a consequence of working from the description alone. **A third failure mode beyond fire/skip: correct activation with no completed output.** A 2026-08-01 Haiku 4.5 "tl;dr README.md" run (`4e5024b4`) called both `context-summarize` and `english-practice` correctly and read `README.md`, but the assistant then treated the skills' injected `isMeta` instruction turns as if they were the user's actual request, replying with meta-commentary summarizing what each skill does and asking "What would you like me to help with?" — the requested README summary was never produced. So a full trace of correct `Skill(...)` calls is still not sufficient evidence the turn succeeded; check that the reply answers the original ask, not just that the right tools fired.

**A model can loop indecisively and then falsely claim it wrote a file** — confirmed 2026-07-31 (`932235ae`, Haiku 4.5): asked to wrap up and update `.claude/SESSION.md`, the model read the file eight times back-to-back with byte-identical results, never called `Write` or `Edit` (it even ran a spurious `ToolSearch(select:Write)`, not realizing `Write` is a base tool needing no lookup), then ended the turn with "Session wrapped up and recorded in SESSION.md" — the file's mtime on disk proved otherwise. This is a different failure from the trigger-skip cases above (which are about whether `Skill(...)` gets called): here the skill fired correctly, but the model's own completion claim was fabricated. Mitigation: treat "I've updated X" as unverified until `git status`/`git diff`/file mtime confirms it, particularly for Haiku-class models finishing multi-step file edits. **The false-completion claim is not guaranteed to repeat, even on the identical prompt and model**: a sibling session the same day (`bdc765b4`, Haiku 4.5) hit the same redundant-reads-then-no-write pattern (five reads of `.claude/SESSION.md` plus one of root `SESSION.md`, a spurious `ToolSearch(select:Edit)` failing for the same reason) but this time stopped short of claiming the file was updated, instead ending with a next-steps question — so the reads-without-writing behavior is the reliable part, and the fabricated success message is a separate, less consistent failure on top of it. **The fabrication isn't confined to live chat replies — it can land in the persisted record itself.** Confirmed 2026-08-01: a SESSION.md entry for transcript `ffb522f2` claimed "this session backfills the memory (`feedback_indentation_tabs.md`) since Write is available here," but at the time that entry was written, no such memory file existed on disk and `MEMORY.md`'s index didn't list it — the backfill claim was itself false, just like the in-chat "I've updated X" pattern above, except written straight into the audit trail meant to catch this kind of thing. Compounding it: once a later session did create that memory file, its content ("repo uses tabs, not spaces") also turned out to be unverified — a repo-wide grep found zero tab-indented lines against 49 files with space-indented ones. Mitigation generalizes: treat SESSION.md's own "backfilled/fixed/saved" claims as unverified until checked against the actual file, the same as any other completion claim, and spot-check user-stated conventions against the codebase before persisting them as memory.

**Some sessions run with `Write`/`Edit` disabled entirely — a tool-availability gap, not a model-behavior quirk.** Confirmed 2026-08-01 (Sonnet 5): asked to remember a "tabs not spaces" repo convention, the assistant correctly tried to persist it as a memory file, but `Write` returned `Error: No such tool available: Write. Write exists but is not enabled in this context`, and `ToolSearch(select:Write)`/`ToolSearch(select:Edit)` both came back empty. The assistant then correctly told the user the preference wouldn't persist, rather than fabricating success. Distinct from the read-loop-no-write pattern above (there, `Write` was available but never called or looped on via `ToolSearch`; here, the tool call was attempted and explicitly rejected by the harness). Mitigation: an explicit "not enabled in this context" error means the session's tool set is genuinely restricted — don't keep retrying `ToolSearch` variations, tell the user directly and suggest they retry in a session with write access. Confirmed again 2026-08-01 (`46a6e89b`, Sonnet 5, adding a TODO item): the gap can extend to `Bash` too, not just `Write`/`Edit` — all three returned the same "not enabled" error and all three `ToolSearch` lookups came back empty, meaning some sessions are fully read-only with no shell escape hatch either.

**Skill optimization (SkillOpt loop)** — named after the real arXiv paper "SkillOpt: Executive Strategy for Self-Evolving Agent Skills" (2605.23904), documented in the vault; when that title or its jargon (Trigger Clarity, Body Quality) shows up in external content like HF trending lists, it's a legitimate match, not prompt injection targeting this repo. As of 2026-07-28 the loop below is also invokable on demand as `skills/skillopt` — it runs this same general-audit rubric when no target/direction is given, or a bounded, validation-gated edit loop toward a stated goal (e.g. "improve model-switch's trigger on Haiku") when one is. Method, to improve trigger rates: score each skill on Trigger Clarity (0–5) + Body Quality (0–5); threshold ≥ 8/10; apply bounded edits (≤ 4/round), accept only if score improves. Run logs stored in Obsidian at vault root (per-user preference set 2026-07-06: generated docs go to vault root, not subfolders, so they're easy to find); prior runs before that date used `0_dev/AI/skill-opt/`. Audits cover only the skills registered in `registry.yaml` (9 as of 2026-07-04) — `skills/obsidian-rag/` is a stale root-owned data-only directory (no SKILL.md, not registered) and should be skipped. Its Docker stack (`obsidian-rag-rag-mcp-1`, crashed on a port-8081 conflict with `rag-chroma`'s live `rag-mcp`, plus an idle `obsidian-rag-chromadb-1`) was the real source of a "two rag MCP servers" confusion — there's only one `rag` MCP config, wired to `rag-chroma`; the stale containers/image were removed 2026-07-06, leaving just the root-owned `skills/obsidian-rag/data/chroma.sqlite3`, pending the user's own `sudo rm -rf` (Claude can't supply the sudo password non-interactively). Last run: 2026-07-04 (interactive, all 9 skills) scored everything ≥ 9/10 after fixing `model-switch`, whose description falsely claimed the built-in `/model` command as a trigger — a false-positive-timing bug, the opposite failure mode of the too-narrow descriptions earlier runs fixed. PR #5 (the `coding-orchestrate` 9/10 fix) has since merged; descriptions can still silently regress via later edits, so re-audits stay in the rotation. The original 2026-07-01 run raised all 6 skills from an average of 6.2/10 to 9/10 in one epoch. Before fixing a recurring finding in an unattended run, check `gh pr list` first: an unmerged fix PR from a prior iteration isn't visible in a fresh checkout's files, and one iteration already opened (then had to close) a duplicate PR #6 this way.

**An automated trigger verifier does exist — use it instead of subagent judgment.** `skills/skillopt/SKILL.md` still claims "no automated verifier exists for 'does this skill trigger well'," which 2026-07-30 disproved: run the candidate against fixed probe prompts with `claude -p "<prompt>" --model <id> --output-format stream-json --verbose` and grep the stream for `"name":"Skill"` — TRIGGERED/SKIPPED per probe, several probes in parallel, no human in the loop. The prior night's run had scored the same skill 9/10 through the fresh-subagent gate while it was in fact triggering **0/4** on Sonnet 5, so a paper score is not evidence; measure, and take 2 passes per candidate since single probes are noisy. Cron/proxy rules apply to the probe wrapper (`http_proxy`/`https_proxy` at `127.0.0.1:10808`, `NODE_USE_ENV_PROXY=1`). Two hard gotchas: (1) **`--allowedTools Skill` does not restrict a `claude -p` probe agent** — probes run in the repo under test with full write access and one of them silently appended unrequested sections *and* a false claim to this `CLAUDE.md` mid-run; always pass `--disallowedTools Bash Edit Write NotebookEdit Task mcp__obsidian__vault_write mcp__obsidian__vault_append mcp__obsidian__vault_patch mcp__obsidian__vault_delete`, and diff the repo after a probe batch. (2) Probe batches burn the 5h window fast — the 2026-07-30 run died on the session limit mid-candidate-B, leaving no report and an empty run dir (`.claude/skillopt-runs/english-practice-20260730-090726/`), so write the run log incrementally rather than at the end.

**MCP server config lives in `settings.json`**, under the `mcpServers` key:

- `~/.claude/settings.json` (global) — available in every project and session; right for general-purpose servers (RAG, Obsidian).
- `.claude/settings.json` (project) — only that repo; extends/overrides global; right for repo-specific servers (e.g. a project database MCP).

**To auto-wire an MCP server on skill install**, extend `install.sh` to write the `mcpServers` entry into the appropriate `settings.json` after symlinking the skill.

**`update-config` skill** can edit `settings.json` interactively (permissions, hooks, env vars, `mcpServers`); invoke it when you need Claude to add or modify a config entry.

**Enabling project-level MCP servers requires two files in the cwd**, not just `settings.json`:

- `.mcp.json` — server definitions (name, command, args, env)
- `.claude/settings.local.json` — `{ "enabledMcpjsonServers": ["server-name", ...] }` so Claude Code actually loads them in that project
- `install.sh`'s `merge_mcp_config` handles writing both; `ldn`'s "inject MCP" option calls it. Syncing to `~/.config/claude-code/mcp.json` is **not** the right mechanism.

**`ldn` manages project-scoped skills, not global** — when you run `ldn` from any project directory, it installs/removes skills into `cwd/.claude/skills/` via `--project`. Pre-selection checks only the cwd, so globally-installed skills (in `~/.claude/skills/`) do not appear pre-checked. Each project gets its own independent set.

**`ldn` "inject MCP" option** — selecting it in the `gum choose` UI calls `install.sh`'s `merge_mcp_config` for every skill that ships an `mcp.json`, writing server definitions and `enabledMcpjsonServers` into the cwd. The item is pre-checked when `.mcp.json` already exists in the cwd.

**Pro/Max usage % IS queryable headlessly via the OAuth usage endpoint** (corrected 2026-07-03; the earlier "interactive statusline hook is the only source" belief was wrong) — `GET https://api.anthropic.com/api/oauth/usage` with `Authorization: Bearer <accessToken from ~/.claude/.credentials.json>` + `anthropic-beta: oauth-2025-04-20` returns `five_hour`/`seven_day` utilization, reset times, and model-scoped weekly limits. `skills/claude-maxer/fetch_usage_oauth.py` wraps this (proxy-aware) and writes `~/.claude/state/usage_snapshot.json`, which `skills/claude-maxer/check_usage.py` gates on (skip at ≥95%); `run_maxer_work.sh` refreshes it before each iteration, and a crontab entry runs it every 15 min, so the snapshot stays fresh with zero interaction. The script also refreshes the ~8h OAuth token itself (single-use refreshToken rotated via `console.anthropic.com/v1/oauth/token` with Claude Code's public client_id, written back to the credentials file atomically) — no interactive session needed, ever; exit 2 now means the refresh itself was rejected (re-login required). The patched `~/.claude/scripts/statusline.py` still caches interactive renders' `rate_limits` to the same snapshot as a passive fallback, and iteration/wall-clock caps + 429 detection remain the backstop. Note: `claude -p` output itself still never includes `rate_limits`, and a Playwright scraper of claude.ai/new#settings/usage (`fetch_usage_web.py`, kept as fallback) is blocked at login by Cloudflare's human check.

**Obsidian MCP doesn't connect in unattended runs** — the `obsidian` server in `.mcp.json` expands `${OBSIDIAN_MCP_TOKEN}`/`${OBSIDIAN_MCP_URL}`, but those env vars are only set in interactive shells — and split across two files: the token in `~/.zshrc.local`, the URL (`http://127.0.0.1:27123/`) in `~/.zshrc` — so headless/cron sessions get no `mcp__obsidian__*` tools (the `rag` server, which needs no env vars, still connects). Workaround for vault work in unattended sessions: `source ~/.zshrc.local` in Bash for the token, set `OBSIDIAN_MCP_URL=http://127.0.0.1:27123/` explicitly (sourcing `~/.zshrc.local` alone leaves it empty), and use the Local REST API `curl` fallback the obsidian-local skill documents. Confirmed 2026-07-02/03 (news-digest runs). Gotcha for any curl fallback: `OBSIDIAN_MCP_URL` ends in `/`, so naively appending `/vault/...` yields a `//` URL the REST API 404s — always build URLs as `${OBSIDIAN_MCP_URL%/}/vault/...`. This silently broke learning-instruct's vault write for weeks (its 404ing reachability probe made it always take the local-storage fallback; fixed 2026-07-11, `401474ba`).

**Unattended scheduling needs a real OS crontab, not `CronCreate`** — the session-scoped `CronCreate` only fires while a Claude Code REPL is idle, so claude-maxer's work loop (`skills/claude-maxer/run_maxer_work.sh`) is wired via `crontab -e` entries instead. Cron gotchas: its minimal env lacks `PATH` (`~/.local/bin`, where `claude` lives), `HOME` (breaks `~/.claude/.credentials.json` lookup), and `http_proxy`/`https_proxy` — this machine reaches api.anthropic.com only through the local xray proxy at `127.0.0.1:10808`, so without the proxy vars every `claude -p` fails with `403 Failed to authenticate` (root-caused 2026-07-02 after all 8 iterations of the first real fire silently failed; the script now exports all three). Cloud scheduled routines (via `RemoteTrigger`) run regardless of this machine's power state but ignore `allowed_tools` restrictions — they always get the default tool preset, so safety must come from the prompt. The local work-loop crontab entry was **disabled 2026-07-03** (commented out, not deleted) after weekly usage ran over expectation; the cloud keep-alive ping still fires.

**Fixed-time pings can't pin the 5h window reset** — the 5h limit is a rolling window that opens on the *first* request after the previous window expires, whatever its source (interactive session, cloud ping, or local work loop). Any usage landing before a scheduled ping opens the window instead, so reset times drift off the planned slots (confirmed 2026-07-03: reset at 20:00 despite pings scheduled for 6/11/16/23/1 Shanghai). No cron design can force fixed reset points.

**Nextcloud app passwords can be minted headlessly** — `docker exec -u www-data mynextcloud-nextcloud-1 php occ user:auth-tokens:add -n --name=<label> <user>` creates an app password *without* the login password (it prints a "limited capabilities" warning, which only affects operations needing the login password — WebDAV is unaffected). Nextcloud runs at `http://127.0.0.1:8080` (container `mynextcloud-nextcloud-1`, users `jing`/`lidaning`). The `nextcloud-paper` skill's MCP server (`uvx nextcloud-mcp-server`, `--enable-app webdav`) reads `NEXTCLOUD_HOST`/`NEXTCLOUD_USERNAME`/`NEXTCLOUD_PASSWORD` from `~/.zshrc.local` — same interactive-shell-only gotcha as the Obsidian vars, so unattended sessions must `source ~/.zshrc.local` and use the curl WebDAV fallback in the skill.

**Instruction-level directory scoping is the pattern for credentials that can't be scoped themselves** — Nextcloud app passwords aren't path-scoped (the `claude-code` app password can reach the whole account), so `skills/nextcloud-paper/SKILL.md` enforces an allowlist in its body instead: an `<!-- ALLOWED_DIRS:BEGIN/END -->` block the user edits directly, with rules requiring every path argument (including both endpoints of a move/copy and search scopes) to resolve inside an allowed directory, and out-of-scope search results dropped before display. Since installed skills are symlinks, allowlist edits take effect on the next activation with no reinstall. This is a soft boundary the model must honor, not one Nextcloud enforces — reuse it for any future skill whose underlying credential is broader than the access the user wants to grant.

**`settings.json` `env` block injects into tool subprocesses only, not the Claude Code client itself** — confirmed 2026-07-04 during model-switch testing. Writing `"ANTHROPIC_BASE_URL": "http://localhost:8787"` into `~/.claude/settings.json`'s `env` key makes the var visible in `echo $ANTHROPIC_BASE_URL` (Bash tool calls), but the Claude Code client reads its own API-routing env vars at **process launch time** and does not re-read settings.json mid-session. This means mid-session settings `env` changes cannot reroute an already-running session's model/provider. To change the client's routing, the var must be set before `claude` starts (shell export, `env` in the launch command, or settings.json `env` written *before* launch). Proxied sessions should export `ANTHROPIC_BASE_URL` in the shell profile or use the settings `env` block as a convenience only — it will affect the *next* launch, not a running one.

**Node's `fetch()` ignores `http_proxy`/`https_proxy`** — unlike curl, a Node process using `fetch()` connects directly, so on this machine (api.anthropic.com reachable only via the xray proxy at `127.0.0.1:10808`) it gets the region-block 403 — which Claude Code misreads as an auth failure and answers with endless "Please run /login" prompts even though credentials are fine. Fix: launch with `NODE_USE_ENV_PROXY=1` (Node ≥ 24) so `fetch()` honors the proxy env vars; model-switch's `switch.sh start`, `shell-setup.sh`, and SKILL.md all set it (root-caused 2026-07-04 after the model-switch proxy's Anthropic passthrough had been silently broken the whole time). This is the Node twin of the cron proxy-vars gotcha above.

**model-switch is controlled out-of-band via `switch.sh`, not the `/model-switch` skill** — a Claude-session-based switcher is unreachable exactly when rate-limited, so `skills/model-switch/switch.sh` (plain curl + python3, no Claude involved) is the control plane: start/stop the proxy, `use <provider>/<model>`, `off`, `status`, keeping `~/.claude/settings.json`'s `ANTHROPIC_BASE_URL` and the proxy's override consistent. The override persists to `~/.claude/state/model-switch.json` and reloads on proxy start, and the proxy's catch-all stubs **any** non-2xx Anthropic response (not just 401/403) so startup endpoints (`/v1/me`, OAuth checks) never block launch during a 429/outage. Gotcha: flipping the override while your own session routes through the proxy reroutes the session you're in — confirmed 2026-07-04 when a test switch to DeepSeek made the live Fable session fail with `400 content[].thinking`. Design settled 2026-07-04: the skill stays as a thin conversational front-end (it can't be the actuator — a skill is markdown that only acts through a live agent), with a pending refactor for the SKILL.md picker flow to delegate to `./switch.sh use`/`off` so the script is the single source of truth (tracked in `.claude/TODO.md`; work parked).

**Installed SKILL.md files are symlinks** — `install.sh` symlinks the repo's skill directory, not copies. Editing `skills/<name>/SKILL.md` in the repo takes effect immediately in the installed skill; no re-install needed. Confirmed: `~/.claude/skills/<name>` and `.claude/skills/<name>` both resolve back to the repo path.

**The harness can silently swap the model mid-session** — when Fable 5's safeguards flag a reply, Claude Code retries it on Opus 4.8 (a `model_refusal_fallback` event in the transcript) without any user action. The statusline is then the reliable indicator: `statusline.py` renders `payload.model.display_name` straight from the harness, which tracks the actual serving model, while the model's injected self-ID string can stay stale at "Fable 5". Confirmed 2026-07-03 when the statusline showed Opus 4.8 mid-conversation and the assistant wrongly insisted nothing had switched. A third, unrelated Fable 5 stop condition exists: a **usage-credits gate** ("Fable 5 requires usage credits. Run /usage-credits to continue or switch models with /model", seen 2026-07-30) that kills the turn outright — no fallback model, no tool calls, nothing in the transcript but the notice. It is separate from the 5h/weekly rolling windows the OAuth usage endpoint reports, so a healthy `usage_snapshot.json` says nothing about whether Fable 5 will actually answer.

**`git mv` fails on a never-committed skill directory** — `git mv skills/<name> skills/<new-name>` errors with "source directory is empty" if `skills/<name>` has no tracked files yet (git has nothing to move), even though the directory clearly has content on disk. Fall back to plain `mv` plus manual `git add` of the new path. Confirmed 2026-07-03 renaming `nextcloud` → `nextcloud-paper` before its first commit; also remember to fix the installed symlink under `.claude/skills/<name>/SKILL.md`, which still points at the old path after a manual `mv` and won't resolve until repointed.

**Two untracked transcript-extraction helpers sit at the repo root** — `extract_transcript.py` and `extract.jq`, both walking a Claude session JSONL into readable per-message text (used for the transcript-reading sessions that produce SESSION.md entries). They are not skills and not registered anywhere. **`extract.jq` is currently broken**: line 6 reads `.role` after piping into `.message.content[]`, where `.` is the content block and has no `role`, so `"--- " + null` aborts jq on any array-content line — the Python version works only because it binds `role` before looping. The fix (`.message.role as $role` before the array pipe) was proposed 2026-07-30 but left unapplied pending the user's go-ahead; prefer the Python script until then.
